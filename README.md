# fairlease

按优先级发放租约的公平分配器，纯标准库，无外部依赖。

## 现状

`fairlease/lease.py` 提供 `FairLease`：

- `FairLease(clock=time.monotonic, aging=5.0)`：clock 为注入时钟，aging 为老化窗口秒数
- `request(node, prio, timeout=None)`：登记一条请求并返回凭据 ticket；prio 越小越优先，timeout 为最长等待秒数，None 表示不设上限
- `grant()`：发放一条租约并返回 node，队列里没有可发放的请求时返回 None
- `pending()`：仍会参与下一轮发放的 node 列表，按服务顺序排列
- `cancel(ticket)`：撤销尚未发放的请求，返回是否真的撤掉
- 内部记录每条请求的入队时刻与递增 ticket，ticket 顺序即先来后到

## 契约

- 优先级数字越小越优先，同优先级按先来后到。
- 一条请求从入队起等待达到 aging 即视为老化，排到所有未老化请求前面；多条老化请求之间仍按先来后到。老化保证任何请求在有限时间内被发放。
- `cancel` 之后请求立即出队，不再参与发放。
- 请求等待时间超过 timeout 即作废并移出队列；恰好等于 timeout 的那一刻仍视为有效。

## 问题

线上出现低优先级长期拿不到租约、同优先级乱序、撤单不生效、
超时边界误杀几处毛病。

## 实现说明

队列保存在 `ticket -> Request` 的字典里，ticket 从 1 单调递增，
既是请求凭据，也是入队先后的唯一依据；每轮发放（`grant` /
`pending`）先按当前注入时钟做一次超时清理，再用排序键给出服务顺序。

- **老化提升（防饿死）**：请求的等待时长 `now - arrival >= aging`
  即视为老化。排序键第一段是老化标志：所有老化请求整组排在未老化
  请求之前，新来的高优先级流量无法插进老化组。老化组内排序键退化为
  纯 ticket 序——一旦老化，优先级不再起作用，只认先来后到。因此一条
  请求的命运是有界的：等够 `aging` 后，它只需排在老化组里同批等待者
  的后面；而每个老化等待者一旦被发放就永久离队，组内排在它前面的
  数量只减不增，所以它在老化之后的有限轮 `grant` 内必被服务，不会被
  持续涌入的高优先级无限期饿死。未老化组仍保持“prio 小者优先”。
- **同级顺序**：排序键末段是 ticket。未老化请求按 `(prio, ticket)`
  排，同优先级严格按入队先后；老化请求按 ticket 排。旧实现按
  `node` 名字母排序的 tie-break 已移除，node 可以是任意不可比较对象。
- **撤单语义**：`cancel(ticket)` 直接从队列字典中 `pop` 掉该请求，
  立即出队，下一轮排序与发放都看不到它，不会再占走发放名额。对已
  发放、已超时清理或不存在的 ticket 撤单返回 `False`；重复撤单第二次
  起也是 `False`。
- **超时边界**：清理条件是严格的 `(now - arrival) > timeout`。等待
  时间“超过”上限才作废；恰好卡在 `now - arrival == timeout` 的请求
  仍有效，照样可以在这一轮被发放。`timeout=None` 的请求永不过期。

排序键汇总为三元组：老化请求 `(0, ticket, ticket)`，未老化请求
`(1, prio, ticket)`；第一段决定老化组整体在前，后两段决定组内次序。
全部实现只使用标准库（`time`），无第三方依赖。
