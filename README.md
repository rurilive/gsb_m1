# vecpage

按版本维护的页表，纯标准库，无外部依赖。

## 现状

`vecpage/page.py` 提供一个 `PageTable`：

- `PageTable()`：空表，初始版本号为 0
- `map(page, frame, ver)`：把 page 在 ver 版本上映射到 frame
- `walk(page, ver)`：读出 page 在 ver 版本对应的帧，没有映射返回 None
- `unmap(page)`：取消 page 的映射，返回是否真的取消掉了
- `rollback(ver)`：把页表回滚到 ver 版本，丢掉该版本之后的记录
- `version()`：最近一次写入用到的版本号
- `MappingConflict`：同一页面在同一版本上被映射到不同帧时使用的异常类型

每个页面维护一串按版本号升序的 `(版本, 帧)` 记录，帧为 None 表示从该版本起
取消映射；`unmap` 产生的取消记录打在递增之后的新版本上。内部一把锁保护，
多路写入同时进来不会把表写坏。

## 问题

版本化页表上线后出现翻页错乱：按旧版本翻页翻到新帧、取消映射把历史版本一起
抹掉、回滚后页表项仍是新值、同页同版本的并发写入互相覆盖且不报冲突。

- 现有行为与 `tests/test_page.py` 基线保持不变（基线一个字不改）

## 实现说明

四个口径都围绕“每个页面一串按版本号升序的 `(ver, frame)` 记录”这一条数据
结构，帧为 `None` 的记录是墓碑，表示从该版本起取消映射。所有方法都在同一把
`threading.Lock` 下执行，冲突检测和写入是一个临界区，并发写入不可能绕过判定。

- **回溯取值（`walk`）**：取该页面记录里版本号不大于请求版本的最后一条。
  记录只表示“从这个版本起帧变成了谁”，在被下一条记录取代之前一直有效，所以
  版本 1 写帧 100、版本 2 写帧 200 之后，`walk(p, 1)` 是 100、`walk(p, 2)` 是
  200；没有不大于请求版本的记录（含取到墓碑）时返回 `None`。用
  `bisect_right` 定位，乱序补写的旧版本记录会按版本号插入正确位置。
- **取消记账（`unmap`）**：不删历史，只往记录末尾追加一条
  `(now + 1, None)` 墓碑，版本时钟推进到 `now + 1`。因此取消只对新版本生效，
  旧版本的帧照样查得回来；取消后再 `map` 要用新版本号，从该新版本起恢复。
  页面当前已经是未映射状态（最后一条是墓碑或从未映射）时返回 `False`，不重复
  记账。
- **回滚口径（`rollback(ver)`）**：物理丢弃所有版本号大于 `ver` 的记录，只留
  `v <= ver` 的前缀，页面若一条不剩就整页移除；版本时钟收回到
  `min(now, ver)`。回滚点之后的换帧和取消都当作没发生过，所以回滚后读任何版本
  得到的都是回滚点当时的状态，之后还能正常写入新版本。
- **冲突判定（`map`）**：仅当“同一页面、同一版本号”已存在记录时才比较帧：
  帧相同视为幂等重复写入，直接放行；帧不同（含已有记录是墓碑）抛
  `MappingConflict`，已有记录保持不动。不同版本号的换帧是正常版本演进，不算
  冲突；不同页面共用同一个帧也不受限制。
