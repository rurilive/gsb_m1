# guardcache

规则服务的进程内多级缓存，命中直接用，未命中回源加载，纯标准库，无外部依赖。

## 模块说明

`guardcache/cache.py` 提供 `GuardCache(loader, ttl=None, capacity=128,
negative_ttl=30, hot_capacity=None, clock=time.monotonic)`：

- 两级结构：热层（`hot_capacity`，默认与 `capacity` 相同）与主层（`capacity`）。
  命中主层会提升到热层，两层共享同一条记录，存活时刻始终一致
- `get(key)`：命中缓存直接返回；未命中调用 `loader(key)` 回填后返回
- `loader` 由调用方提供，签名 `loader(key) -> value`；抛 `NotFound` 表示 key
  不存在，缓存据此记入负缓存，`get` 随之抛出 `NotFound`
- `loader` 抛其它异常时**不写任何缓存条目**，异常原样上抛，下一次 `get`
  会重新回源，瞬时抖动不会把坏值（包括 `None`）钉进缓存
- 同一个 key 的并发未命中只放一个 `loader` 出去（请求合并 / singleflight），
  其余请求阻塞等同一趟结果：不打惊群，也不会出现慢请求后写入、旧值覆盖新值
- `ttl`：正条目存活秒数，`None` 表示永不过期
- 过期时刻在条目**写入时**一次性算死，读取命中只刷新 LRU 顺序、不续期，
  热 key 被读得再频繁，TTL 到点也一样重新回源
- `negative_ttl`：负条目存活秒数，`None` 表示永不过期
- `invalidate(key)`：删除该 key 的正/负缓存条目，返回是否真的删掉了
- 容量满时按 LRU 顺序驱逐，且优先驱逐正条目、保护负条目；只有整层全是负
  条目时才退回最旧的负条目，避免“确认不存在”的占位先被挤掉
- 内部一把锁保护，`loader` 在锁外执行（可以慢慢跑，不阻塞其它 key）
- `clock`：时间读取统一走它，便于测试注入

## 计数器

`stats()` 返回计数快照，每次调用返回新 dict：

- `hits`：读取被缓存直接满足的次数（正、负条目都算）
- `misses`：需要回源处理的读取次数
- `loads`：实际调用 `loader` 的次数
- `evicted`：因容量被驱逐的条目数
- `negatives`：写入的负条目数

并发未命中被合并时，等待的请求各计一次 `misses`，但只有领头的请求计一次
`loads`。


## Known Issues

以下四个问题已修复，记录现象、根因与修法备查。

### 1. 上游抖一次，某些 key 之后一直拿到空结果，只能重启

- 现象：某个 key 回源超时一次以后，再请求始终拿到空结果，换 key 正常，
  必须重启进程才恢复。
- 根因：旧实现的 `_load` 在 `except Exception` 分支里调用
  `self._remember(key, None)`，把 `None` 当成一个合法值写进了缓存。超时、
  连接错误这类瞬时故障于是被固化成一条带 TTL（甚至永不过期）的“坏值”条目，
  后续请求全部命中它，永远不再回源。
- 修法：只有回源成功和 `NotFound` 才写缓存；其它异常原样上抛、不留任何
  条目，下一次 `get` 自然重新回源，抖动过去后立即自愈（见 `_load`）。

### 2. 热门 key 并发回源，最慢的请求把旧快照写进缓存

- 现象：热配置 key 被多个请求同时访问时，好几个 `loader` 一起跑，最后
  缓存里留下的是最慢那次带回的旧快照，之后所有请求都读旧值。
- 根因：旧实现发现未命中后每个请求各自直接调 `loader`，没有任何并发
  去重；多个回源并发时，谁后结束谁最后写入，与数据新旧无关，慢请求的旧
  快照因此覆盖了快请求的新快照。
- 修法：加 per-key 的在途航班（`_inflight` + `_Flight`）。未命中时若该
  key 已有回源在跑，后来者在锁外等同一趟结果（值或异常共享），只有领头
  请求调一次 `loader` 并回填，惊群和旧值覆盖一并消除；不同 key 仍各自
  独立回源。

### 3. 五分钟 TTL 的开关被读个不停就一直不生效

- 现象：开关 key 配了 5 分钟 TTL，上游改完超过 5 分钟仍不生效，只要一
  直有读取就一直返回旧值。
- 根因：旧实现在热层/主层的命中路径上都执行了
  `entry.expires_at = self._fresh_expiry(...)`，每次读取都把过期时间向后
  推一个 TTL（滑动过期）。热 key 两次读取间隔永远小于 TTL，条目于是永远
  不过期。
- 修法：删除命中路径上的续期逻辑，过期时刻只在 `_remember` 写入时计算
  一次；命中只更新 LRU 顺序。TTL 从写入时刻起固定倒计时，到点必换新。

### 4. 查不存在的 key，负缓存占位一满容就先被挤掉，下游被打爆

- 现象：`loader` 已明确返回 `NotFound`，本该记一笔负缓存；但缓存一装
  满，这些占位最先被驱逐，同一个不存在的 key 被反复回源。
- 根因：旧实现的驱逐是无条件的 `popitem(last=False)`，正负条目共用一个
  LRU 池、没有任何区分。负条目通常最先写入、之后不再移动，自然排在 LRU
  最旧端，容量一紧就先被挤掉；挤掉后幽灵 key 立刻穿透到下游。
- 修法：驱逐选牺牲者时（`_evict_lru`）先沿 LRU 最旧端找最久未用的
  **正条目**，找到就驱逐它、保住负占位；只有整层全是负条目时才退回驱逐
  最旧的负条目。主层和热层用同一套规则，容量内的“确认不存在”不再被正常
  数据挤掉，幽灵 key 不会反复打下游。
