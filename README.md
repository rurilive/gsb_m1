# ringbuf

多生产者/多消费者定长环形缓冲，网关进程内嵌使用，纯标准库（threading.Lock）。

## 语义

- `put(item)`：写入一个元素，永不阻塞；缓冲满时覆盖最老元素，count 不会超过容量
- `get()`：取出最老元素；缓冲为空时抛 `ringbuf.Empty`；每条消息只会被一个消费者取到
- `count()`：当前元素个数，取值范围 [0, capacity]
- `snapshot()`：按逻辑顺序（写入顺序）导出当前内容的副本，不影响缓冲状态
- 所有操作线程安全，可在多线程读写场景下直接使用

## 运行

```bash
python3 demo.py
```

## Known Issues

以下问题均已修复（2026-09），记录根因备查：

1. **count 只涨不跌、超过容量，可用容量越跑越大**
   - 根因一：`put` 在缓冲满时调用 `_advance_head()` 淘汰最老元素后仍然无条件执行
     `self._count += 1`，覆盖场景下计数多涨一次，最终大于容量。
   - 根因二：`get` 把 `_advance_head()` 和 `self._count -= 1` 放在锁外，多消费者并发时
     `count -= 1` 会发生丢失更新（lost update），且计数可能减成负数。
   - 修复：覆盖时 head/tail 同步前移且计数保持不变，仅新增写入才 +1；`get` 的取值、游标
     推进、计数递减全部收进同一把锁的临界区内。

2. **两个消费者拿到同一条消息（重复消费）**
   - 根因：`get` 只在锁内读取 `self._buf[self._head]`，随后释放锁再推进 head；
     两个消费者可以在 head 尚未前进时读到同一个槽位，下游因此收到重复消息。
   - 修复：head 推进移入临界区，出队成为原子操作，每条消息至多被一个消费者取到。

3. **生产确认写入、缓冲未满，但消费端少收消息**
   - 根因：tail 回绕条件是 `> capacity`（合法下标范围 0..capacity），head 回绕条件却是
     `>= capacity`，两者不一致。head 走到下标 `capacity`（物理最后一格）时被提前重置为 0，
     该槽位永远不会被读取，之后还会被当成 head 读到陈旧数据。写入未触发覆盖时，消息就这样
     静默丢失。
   - 修复：统一使用 `_advance(cursor)`，回绕条件与 tail 一致为 `> capacity`，每个槽位都能
     正常读空；出队后清空槽位引用，避免残留陈旧对象。

4. **snapshot 导出顺序与写入顺序不符**
   - 根因：`snapshot` 直接返回物理数组 `self._buf` 的前 `count` 个槽位，既没有从 head
     开始（head 回绕后最老元素在数组中段或末尾），回绕时也没有跨数组末尾拼接。
   - 修复：以 head 为起点按逻辑顺序切片，跨越数组末尾时拼接头部，保证导出顺序即 FIFO 顺序，
     且长度与 `count()` 一致。

防回归测试见 `tests/`（`python3 -m unittest discover -s tests`），含多生产者/多消费者、
覆盖淘汰、并发 snapshot 以及确定性的重复消费竞态用例。
